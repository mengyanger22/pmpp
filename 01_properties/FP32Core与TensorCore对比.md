# FP32 Core 与 Tensor Core：什么时候用、优劣对比

## 一、GPU什么时候用FP32 Core计算，什么时候用Tensor Core

这个判断不是"手动选"，而是**由调用的运算类型、使用的数据类型/API，决定了编译器和硬件自动分流到哪个单元**。

### 核心判断标准：运算模式决定了走哪个单元

**走FP32 Core（普通CUDA Core）的情况：标量/逐元素运算**

CUDA Core擅长的是**一条指令处理一个数据点**的运算，比如：
- 普通的加减乘除（`a + b`, `a * b`）
- 激活函数（ReLU、Sigmoid这类逐元素运算，虽然exp/sigmoid这类可能走SFU）
- 条件判断、逻辑运算
- 大部分不涉及"矩阵乘加"结构的通用计算

**走Tensor Core的情况：矩阵乘加运算（GEMM-like操作）**

Tensor Core专门加速的是 **D = A × B + C** 这种矩阵乘加形式的运算，一次指令处理的是一小块矩阵（比如4×4或更大的tile），而不是单个标量。具体会被路由到Tensor Core的场景：

- **深度学习里的卷积层和全连接层**：这些运算本质上都可以转化成矩阵乘法（卷积通过im2col等方式转换），所以训练/推理时的核心计算基本都在用Tensor Core
- **调用cuBLAS、cuDNN这类库的矩阵乘法/卷积API**：这些库内部会自动检测硬件支持情况，有Tensor Core就优先用
- **PyTorch里直接调用`torch.matmul`、`nn.Linear`、`nn.Conv2d`**：框架底层自动调用cuBLAS/cuDNN，这些库自动决定要不要用Tensor Core

### 决定能不能用Tensor Core的关键因素：数据类型和精度

这是最容易被忽略但很关键的一点——**Tensor Core对输入数据的精度有要求，不是什么精度都能用**：

- **早期Tensor Core（Volta起）**：主要支持FP16输入、FP32累加（混合精度）
- **Ampere架构开始**：支持了更丰富的精度组合，包括 **TF32**（一种专门为Tensor Core设计的19位精度格式，牺牲一点精度换取和FP32接近的数值范围但速度快得多）、BF16、INT8等
- **纯FP32运算**：在Ampere之前，如果坚持用标准FP32精度做矩阵乘法，默认是**走不了Tensor Core的，只能用普通CUDA Core**。Ampere之后，PyTorch等框架可以通过开启TF32模式（`torch.backends.cuda.matmul.allow_tf32 = True`），让FP32输入的矩阵乘法在内部自动转换成TF32去调用Tensor Core，用更快的速度换取略微的精度损失

### 具体到写代码时的实际判断

**写普通CUDA kernel，手写运算逻辑**：
- 如果自己写一个逐元素的kernel（比如vector add、简单的element-wise操作），走的就是普通CUDA Core，没有Tensor Core什么事
- 如果想手动利用Tensor Core，需要用 **WMMA API**（Warp Matrix Multiply-Accumulate），这是CUDA提供的让你显式调用Tensor Core的接口，要求数据按特定的矩阵分块（fragment）格式组织，直接手写比较复杂，一般很少手写这层，更多是通过调用现成的库

**用深度学习框架（PyTorch等）**：
- 框架会自动判断：如果模型用了`nn.Linear`、`nn.Conv2d`这类层，并且输入数据类型/精度设置支持（比如开启了AMP自动混合精度，或者显式用了`.half()`转成FP16），框架底层的cuDNN/cuBLAS会自动调用Tensor Core
- 如果用的是纯FP64（双精度）运算，Tensor Core基本不支持（除非是专门为科学计算设计的某些高端卡有FP64 Tensor Core），会退回到普通CUDA Core（甚至更慢的FP64 Core，如果芯片有专门配置的话）

### 一个直观的判断口诀

**"单点运算用CUDA Core，矩阵乘加用Tensor Core；要用上Tensor Core，精度通常得是FP16/BF16/TF32/INT8这类，不能是严格的FP32/FP64"**

## 二、Tensor Core和FP32相比优劣是什么

这两者本质上是**为不同类型运算设计的专用硬件**，不是单纯的"谁比谁强"，而是"谁在什么场景下有压倒性优势"。

### 吞吐量（算力）：Tensor Core碾压级优势，但只限于矩阵乘加这种运算模式

以Ampere架构为例，**同样一块芯片，Tensor Core跑矩阵乘法的理论峰值算力，通常是同精度下FP32 CUDA Core的8-16倍以上**（具体倍数因架构代际和精度组合而异）。原因是硬件设计上的本质区别：

- **FP32 CUDA Core**：每个时钟周期，一个CUDA Core完成一次标量乘加运算（一个数乘一个数，加到另一个数上）
- **Tensor Core**：每个时钟周期，一个Tensor Core直接完成一个**小矩阵块的乘加运算**（比如一次性算完一个4×4×4的矩阵乘法块），本质上是用硬件直接并行化了多个乘加操作，而不是靠堆砌更多标量ALU核心数量去堆算力

### 适用范围：FP32 Core通用，Tensor Core专用

这是两者最本质的差异，也是为什么不能简单说"Tensor Core完胜"：

**FP32 CUDA Core**：
- 适用于**任意标量运算**——加减乘除、逻辑判断、条件分支、不规则的数据访问模式
- 不要求计算能被组织成矩阵乘加的形式
- 灵活性极高，几乎所有代码都能跑

**Tensor Core**：
- 只擅长**矩阵乘加这一种运算模式**（D = A×B + C）
- 如果计算逻辑没法转化成矩阵乘法的形式（比如大量的条件分支、不规则的数据依赖），Tensor Core完全用不上，这种情况下只能老老实实用CUDA Core
- 对数据的组织格式也有严格要求（需要按特定的tile/fragment排布），不是任意写法都能自动享受加速

### 精度：FP32 Core精度更高，Tensor Core通常要牺牲一些精度换速度

- **FP32 CUDA Core**：标准的IEEE 754单精度浮点，精度稳定、可预期
- **Tensor Core**：早期主要靠FP16输入（精度明显低于FP32），虽然用FP32做累加来部分弥补精度损失，但输入阶段的精度下降是实打实的；即使是Ampere引入的TF32，也是通过**截断尾数位数**（把FP32的23位尾数砍到10位，和FP16看齐，但保留FP32的8位指数范围）来换取速度，本质上也是一种精度妥协

这意味着：**对数值精度要求极高的场景（比如某些科学计算、金融计算），可能必须坚持用FP32 Core，不能冒险用Tensor Core**，哪怕速度慢很多。

### 编程复杂度：FP32 Core简单直接，Tensor Core手动使用门槛高

- **FP32 CUDA Core**：写法符合直觉，普通的`+`、`*`运算符编译器直接映射到CUDA Core指令，没有额外心智负担
- **Tensor Core**：如果想在手写kernel里直接利用，需要用WMMA API，数据要按特定的fragment格式加载、特定的tile大小组织，编程复杂度明显更高。**好消息是日常开发大部分时候不需要手写**——cuBLAS、cuDNN这些库已经把Tensor Core的调用封装好了，PyTorch等框架通过调用这些库自动受益，普通使用者感知不到这层复杂度

### 一个核心结论：不是替代关系，是互补关系

**Tensor Core不是用来取代FP32 Core的，它是给"矩阵乘加"这一类高频、规整的运算量身定制的加速器**，而GPU芯片里同时保留大量FP32 Core，是因为**真实的计算任务里，总有相当一部分是矩阵乘加之外的通用标量运算**（比如激活函数里的部分非矩阵运算、数据预处理、控制逻辑），这些活儿还是得靠FP32 Core来扛。

一个典型深度学习模型的训练过程，**卷积层/全连接层的矩阵乘法部分吃Tensor Core的加速，而LayerNorm、Softmax、各种elementwise操作、数据搬运这些辅助计算，依然在用FP32 Core（或者SFU处理超越函数）**，两者是分工协作、缺一不可的关系，不存在"谁更优"的单一答案，只有"这个具体运算该交给谁"的判断。

### 一句话总结这个对比

**Tensor Core在它擅长的领域（矩阵乘加）里，用牺牲一部分精度和灵活性的代价，换来了数量级的吞吐量提升；FP32 Core则在通用性和精度稳定性上保持不可替代的地位**——这组对比本质上是"专用硬件 vs 通用硬件"的设计哲学：专用硬件在窄场景里效率碾压，但离开那个场景就毫无用武之地，这也是为什么现代GPU要同时集成这两套硬件，而不是押注其中一个。
